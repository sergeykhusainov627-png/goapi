## 1. Краткое описание проекта PyBot-ITAcadem (что переписываем)

**PyBot-ITAcadem** — асинхронный Telegram-бот для IT-академии. Он автоматизирует
"внутреннюю кухню" академии: регистрацию студентов, роли, баллы, уровни,
компетенции и рассылки. Наша задача — перенести **бизнес-логику** этого бота
в **REST API на Go**, заменив Telegram-интерфейс на HTTP-эндпоинты.

### Стек (Python-версия, которую мы заменяем)

| Слой | Технология |
|---|---|
| Язык | Python 3.14 |
| Telegram | aiogram 3 + aiogram-dialog (пошаговые диалоги) |
| БД | PostgreSQL 18, SQLAlchemy 2 (async), Alembic (миграции) |
| Кэш/очереди | Redis (FSM-состояния + брокер задач) |
| Фоновые задачи | TaskIQ (worker + scheduler) |
| Health API | FastAPI (отдельный процесс) |
| DI | Dishka |
| Валидация | Pydantic v2 |
| Инфраструктура | Docker Compose, GitHub Actions, Ansible, Grafana+Loki |

### Бизнес-функционал, который переносим в API

**Пользовательские сценарии:**
- регистрация (контакт → имя → фамилия → отчество → компетенции);
- просмотр профиля: уровни (академический и репутационный), баллы, роли, компетенции;
- просмотр компетенций других пользователей.

**Админские сценарии:**
- начисление/списание баллов (academic / reputation) с указанием причины;
- управление ролями (Student, Mentor, Admin);
- управление компетенциями пользователей;
- рассылки по всем / по роли / по компетенции.

**Role request flow:**
- запрос роли пользователем;
- подтверждение или отклонение запроса администратором;
- защита от повторных запросов (cooldown после отказа, запрет дублей).

**Фоновые задачи:**
- еженедельная публикация лидерборда по расписанию (cron).

### Модель данных (главные таблицы)

```
users                  — пользователи (email, ФИО, телефон, баллы, статус активности)
roles                  — роли (Student, Mentor, Admin)
user_roles             — связь пользователь ↔ роль
competencies           — компетенции
user_competencies      — связь пользователь ↔ компетенция
levels                 — уровни (тип: academic/reputation, порог баллов)
user_levels            — текущий уровень пользователя по каждому типу
points_transactions    — история начисления баллов
valuations             — кто кому и за что начислил баллы
role_requests          — запросы на роль (PENDING/APPROVED/REJECTED/CANCELED)
role_events            — аудит изменений ролей
tasks / task_solutions — задачи и решения (задел на будущее)
achievements           — достижения (задел на будущее)
```

### Архитектура (Python-версия)

Layered Architecture с элементами pragmatic DDD:

```
presentation/  — Telegram-хендлеры, диалоги, клавиатуры, тексты, health API
services/      — бизнес-логика (points, role_request, broadcast, leaderboard...)
domain/        — доменные исключения и сервисы (LevelCalculator)
infrastructure/— репозитории, адаптеры, TaskIQ, порты
db/            — SQLAlchemy-модели
dto/           — DTO и value objects
di/            — DI-контейнер (Dishka)
core/          — конфиг, логгер, константы
```

Рантайм разделён на процессы: `bot`, `taskiq-worker`, `taskiq-scheduler`, `health`.

> ⚠️ **Важно про исходники.** На машине, где актуализировался документ, самого
> Python-проекта нет (нет `alembic.ini`, `pyproject.toml`, каталога бота).
> Поэтому схему БД придётся восстанавливать по списку таблиц из этого документа
> или запросить доступ к репозиторию. Это единственное место в роадмапе, где
> нужен доступ к оригиналам, — см. Фазу 2.

## 2. Моя оценка проекта

### Сильные стороны (чему стоит учиться)

1. **Дисциплина разработки.** Conventional Commits, SemVer, ADR (архитектурные
   решения документируются), шаблоны issues и PR, Kanban в GitHub Projects.
2. **Архитектура.** Layered + pragmatic DDD — разумный баланс. Слои не превращены
   в догму, но разделение ответственности соблюдается. DI, репозитории,
   порты/адаптеры — всё на своих местах.
3. **Тесты и CI.** 90 тестовых файлов, unit + integration (реальный PostgreSQL),
   coverage-порог 80%, quality gate в CI.
4. **Продуманный рантайм.** Разделение процессов, health/readiness API,
   безопасные рассылки (bulk, jitter, retry), rate limiting.
5. **Инфраструктура.** Docker Compose, GitHub Actions (CI/CD), Ansible, observability.

### Слабые стороны и риски

1. **Переусложнение.** Для Telegram-бота стек Grafana+Loki+Alloy+Nginx+Ansible+
   18 ADR — это уровень enterprise-проекта. При переписывании на Go
   **не копируйте это 1-в-1**.
2. **Python 3.14** — очень свежая версия, часть зависимостей может быть нестабильна.
3. **Огромная конфигурация** (десятки env-переменных) — сложно поддерживать.
4. **Rate limiting на in-memory кэше** — известный компромисс: при нескольких
   репликах лимиты перестают работать. На Go сразу делайте на Redis.
5. **Только long polling**, webhook-режим не реализован.

### Итоговая оценка

**8/10 как учебный проект.** Зрелый, хорошо организованный проект, который
отлично подходит как **спецификация бизнес-логики** для переписывания на Go.
Главный урок: не тащите всю инфраструктуру в новый проект — начните с малого
и добавляйте сложность постепенно.

## 3. Что меняется при переходе от бота к API

| Было (Telegram-бот) | Стало (REST API) |
|---|---|
| Команды `/profile`, `/points` | HTTP-эндпоинты `GET /api/v1/users/{id}`, `POST /api/v1/users/{id}/points` |
| Пошаговые диалоги (FSM) | Обычные JSON-запросы: `POST /api/v1/auth/register` |
| Inline-кнопки "одобрить/отклонить" | Эндпоинты `POST /api/v1/role-requests/{id}/approve` |
| Идентификация по `telegram_id` | **JWT-токены** (email + пароль) |
| Рассылка сообщений в Telegram | Уведомления в БД + `POST /api/v1/broadcast` |
| Middleware aiogram | HTTP-middleware (auth, roles, rate limit) |
| FSM-состояния в Redis | Не нужны — FSM-диалогов в API нет |

**Что остаётся неизменным:**
- вся бизнес-логика (баллы, уровни, роли, cooldown, защита от дублей);
- модель данных PostgreSQL (с небольшими изменениями);
- разделение на слои (presentation / services / domain / infrastructure);
- фоновые задачи (еженедельный лидерборд).

> ⚠️ **Уточнение про "stateless".** HTTP-запросы действительно независимы: FSM-состояний
> диалогов в API нет. Но это **не значит, что у API нет состояния вообще** —
> у нас остаются refresh-токены и rate limiting. Просто храним их не как FSM,
> а как обычные данные (см. §4.2 и §8.4).

## 4. Дизайн Go REST API

### 4.1. Стек

> **Проверено на актуальность.** Версии и имена библиотек сверены с
> официальными источниками, потому что в первой версии документа были ошибки.

| Задача | Рекомендация | Почему |
|---|---|---|
| Язык | **Go 1.27** (текущая стабильная) | Первая версия документа говорила "1.24+" — это уже устарело |
| HTTP | **`net/http`** (роутер из Go 1.22+) — см. §4.1.1 | Метод + шаблон пути (`GET /api/v1/users/{id}`) уже в стандартной библиотеке |
| JWT | `github.com/golang-jwt/jwt/v5` | Популярная библиотека; **важно указывать major-версию `/v5`** |
| Пароли | **`golang.org/x/crypto/bcrypt`** | ✅ Исправлено: было `opensourcedapps/bcrypt` — такого поддерживаемого модуля найти не удалось. Официальная реализация живёт в `golang.org/x/crypto` |
| PostgreSQL | драйвер `pgx` + **чистый SQL** | В Go нет доминирующего ORM; чистый SQL — идиоматично и учит SQL |
| Миграции | `golang-migrate/migrate` | Простой CLI, SQL-файлы. **Запускается отдельным шагом, не из API** (§8.3) |
| Redis | `redis/go-redis` | Rate limiting, кэш, очереди. **Refresh-токены в Redis больше не храним** (§4.2) |
| Логирование | `log/slog` (встроено в Go 1.21+) | Структурированные логи из коробки |
| Метрики | `prometheus/client_golang` | Pull-модель: отдаём `/metrics`, Prometheus сам собирает (§9.3) |
| Тесты | `testing` (stdlib) + `testcontainers-go` | Интеграционные тесты с реальным PostgreSQL |
| Rate limiting | Свой token bucket на Redis | Сразу правильно, без компромисса из Python-версии (§8.4) |

> **Важно про Go-мышление:** в Go нет DI-контейнеров и "магии" как в Python.
> Зависимости передаются явно через конструкторы (composition root). Это не минус,
> а фича — код становится проще и прозрачнее.

#### 4.1.1. Выбор HTTP-фреймворка (РЕШЕНИЕ отложено до конца Фазы 1)

Замечание из `Redaction.md`: *"gofiber — возможно стоит пересмотреть выбор
(встроенная библиотека net/http / Gin)"*. Замечание принимается, и вот почему
оно обосновано **сильнее**, чем просто "хочется попроще":

**Главный аргумент против Fiber — не скорость, а `fasthttp`.**
Fiber построен не на `net/http`, а на `fasthttp` — это другая реализация HTTP.
Практические последствия:
- стандартный `http.Handler`-middleware не подключается напрямую — часть
  экосистемы Go просто недоступна;
- тестирование через `httptest` отличается от общепринятого;
- код оказывается завязан на API фреймворка (`fiber.Ctx`), и уход с него — это
  переписывание хендлеров, а не смена обвязки.

**Почему `net/http` сейчас — разумный выбор по умолчанию:**
1. С Go 1.22 в стандартном `http.ServeMux` появились методы и шаблоны путей
   (`mux.HandleFunc("GET /api/v1/users/{id}", ...)`) — то, ради чего раньше брали
   фреймворк, теперь в стандартной библиотеке. Плюс `r.PathValue("id")`.
2. Для новичка это правильный учебный путь: сначала понять `http.Handler`,
   `context`, middleware как цепочку функций — потом уже брать обёртки.
3. Ноль зависимостей на старте.

**РЕШЕНИЕ (рабочее):**
- В Фазе 1 используем `net/http` + стандартный роутер.
- **Жёсткое правило:** хендлеры пишем как обычные `func(w http.ResponseWriter, r *http.Request)`.
  Никаких типов фреймворка в сигнатурах, в сервисах и в домене.
- В конце Фазы 1 (когда есть 5–7 живых эндпоинтов) делаем **ADR "Выбор HTTP-слоя"**
  и решаем окончательно. Если к тому моменту чего-то не хватает — переезд на `gin`
  или Fiber v3 будет правкой одного файла роутера, а не переписыванием проекта.

**Если всё-таки берём Fiber — берём v3 и читаем только v3-документацию.**
Fiber v3 — это отдельная мажорная версия с изменённым API; подавляющее большинство
туториалов и ответов в интернете написаны про v2 и **не скомпилируются** на v3.
Это отдельный источник боли для новичка, что тоже аргумент в пользу `net/http`.

### 4.2. Аутентификация (JWT)

- **Регистрация:** `POST /api/v1/auth/register` — email + пароль + ФИО.
  Пароль хешируем через bcrypt, в БД храним только хеш.
- **Логин:** `POST /api/v1/auth/login` — возвращает пару токенов:
  - `access_token` (короткоживущий, 15–30 мин) — для каждого запроса;
  - `refresh_token` (долгоживущий, 7–30 дней) — для обновления access.
- **Доступ:** клиент шлёт `Authorization: Bearer <access_token>`.
- **Middleware `auth`:** проверяет токен, кладёт `user_id` в контекст запроса.
- **Middleware `requireRole(Admin)`:** проверяет роль пользователя.

#### Где хранить refresh-токены (✅ ИЗМЕНЕНО)

В первой версии было: *"refresh-токены храним в Redis (ключ `refresh:{user_id}`, TTL)"*.
От этого решения отказываемся. Причины:

1. **Redis не нужен, чтобы уметь отзывать токены.** Хешированный refresh-токен
   в PostgreSQL отзывается одним `UPDATE`.
2. **Появляется обнаружение кражи токена.** Если хранить цепочку ротации
   (какой токен на какой был обменян), то повторное использование уже
   использованного refresh-токена — это явный признак кражи. С ключом
   `refresh:{user_id}` в Redis такая проверка невозможна: там лежит только
   "последний".
3. **Минус одна зависимость** в Фазах 1–3. Redis остаётся в стеке, но для
   rate limiting и очередей — там, где он реально нужен.

**Схема:**

```sql
CREATE TABLE refresh_tokens (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    token_hash   BYTEA  NOT NULL UNIQUE,   -- SHA-256 от токена, сам токен не храним
    expires_at   TIMESTAMPTZ NOT NULL,
    revoked_at   TIMESTAMPTZ,
    replaced_by  BIGINT REFERENCES refresh_tokens(id),  -- цепочка ротации
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX ON refresh_tokens (user_id);
```

Правила:
- refresh-токен — **случайные 32+ байта** (`crypto/rand`), не JWT. JWT тут не нужен:
  он самоописываемый, а нам нужна непредсказуемость и запись в БД.
- в БД — только `SHA-256(token)`. Утечка дампа БД не даёт войти.
- при `POST /auth/refresh` — **ротация**: старый помечаем `revoked_at`,
  выдаём новый, `replaced_by` связывает их.
- если пришёл **уже отозванный** токен → это признак компрометации: отзываем
  **всю цепочку** пользователя и требуем повторный логин.

#### Мгновенный отзыв access-токенов

Access-токен — JWT, он самодостаточен, и его нельзя "отозвать" без похода в БД.
Чтобы `logout` и смена роли действовали **сразу**, а не через 15–30 минут:

- в таблицу `users` добавляем колонку `access_token_version INT NOT NULL DEFAULT 0`;
- в access-JWT кладём claim `ver`;
- middleware `auth` сверяет `ver` из токена с `access_token_version` пользователя;
- при `logout`, смене пароля и **любом изменении ролей** — `access_token_version = access_token_version + 1`.

Это одна проверка, которую всё равно нужно делать (мы и так читаем роли для
`requireRole`) — то есть бесплатно. Кэш на 30–60 секунд в Redis (когда он
появится) убирает и этот поход в БД.

### 4.3. Эндпоинты API (v1)

> **Единая терминология (✅ ИСПРАВЛЕНО):** в первой версии ресурс назывался
> `competencies` в одном месте и `competences` в другом. Договорились: **везде
> `competencies`** — и в URL, и в таблицах, и в DTO, и в коде.

**Auth:**
```
POST   /api/v1/auth/register          — регистрация (email, пароль, ФИО)
POST   /api/v1/auth/login             — вход, выдаёт access + refresh
POST   /api/v1/auth/refresh           — обновление access по refresh (с ротацией)
POST   /api/v1/auth/logout            — отзыв refresh-токена + инкремент token_version
GET    /api/v1/auth/me                — текущий пользователь
```

**Пользователи и профиль:**
```
GET    /api/v1/users/{id}              — профиль (уровни, баллы, роли, компетенции)
GET    /api/v1/users/{id}/competencies — компетенции пользователя
GET    /api/v1/users/{id}/points       — история транзакций баллов (пагинация)
```

**Баллы и лидерборд:**
```
POST   /api/v1/users/{id}/points      — [admin] начислить/списать (type, amount, reason)
                                         + заголовок Idempotency-Key (§8.1)
GET    /api/v1/leaderboard            — топ пользователей (?type=academic&limit=10)
```

**Роли:**
```
GET    /api/v1/roles                  — список ролей
POST   /api/v1/roles                  — [admin] создать роль
DELETE /api/v1/roles/{id}             — [admin] удалить роль
POST   /api/v1/users/{id}/roles       — [admin] назначить роль
DELETE /api/v1/users/{id}/roles/{rid} — [admin] снять роль
```

**Role requests:**
```
POST   /api/v1/role-requests          — запрос роли (role_id)
GET    /api/v1/role-requests          — [admin] список запросов (?status=PENDING)
POST   /api/v1/role-requests/{id}/approve — [admin] одобрить
POST   /api/v1/role-requests/{id}/reject  — [admin] отклонить
```

**Компетенции:**
```
GET    /api/v1/competencies           — список компетенций
POST   /api/v1/competencies           — [admin] создать
DELETE /api/v1/competencies/{id}      — [admin] удалить
POST   /api/v1/users/{id}/competencies       — [admin] назначить пользователю
DELETE /api/v1/users/{id}/competencies/{cid} — [admin] снять
```

**Уведомления и рассылки:**
```
GET    /api/v1/notifications          — уведомления пользователя (пагинация)
POST   /api/v1/broadcast              — [admin] рассылка (target: all|role|competence, text)
GET    /api/v1/broadcast/{id}         — [admin] статус/отчёт по рассылке
```

**Health и метрики:**
```
GET    /health                        — liveness (процесс жив, без проверок зависимостей)
GET    /ready                         — readiness (проверка БД и Redis)
GET    /metrics                       — Prometheus (внутренний, не публикуем наружу — §9.3)
```

**Контракт статус-кодов (договорились сразу, чтобы не расходиться):**

| Код | Когда |
|---|---|
| 200 OK | Успешное чтение / обновление |
| 201 Created | Создан ресурс (регистрация, роль, транзакция баллов) |
| 204 No Content | Удаление, logout |
| 400 Bad Request | Невалидный JSON / не прошла валидация полей |
| 401 Unauthorized | Нет токена / токен истёк / неверный пароль |
| 403 Forbidden | Токен валиден, но прав не хватает |
| 404 Not Found | Ресурса нет |
| 409 Conflict | Дубликат (email занят, роль уже назначена) |
| 422 Unprocessable Entity | Бизнес-правило нарушено (баллы уйдут в минус, cooldown активен) |
| 429 Too Many Requests | Сработал rate limit |
| 500 Internal Server Error | Наша ошибка (детали — в лог, не в ответ) |

### 4.4. Модель данных (изменения относительно Python-версии)

```
users:
  id, email (unique), password_hash, first_name, last_name, patronymic,
  phone_number, github_url, join_date, activity_status_id, last_active_at,
```

## 6. GitHub workflow для команды из двух человек

### Базовые правила

1. **`main` — священная.** Никто не коммитит в `main` напрямую.
2. **Ветка на каждую задачу:** `feat/auth`, `fix/points-bug`.
3. **Слияние только через Pull Request** + ревью напарника.
4. **Один PR = одна задача.** Маленькие PR ревьюить легче.
5. **Conventional Commits:**
   - `feat: ...` — новая фича
   - `fix: ...` — исправление
   - `refactor: ...` — рефакторинг
   - `test: ...` — тесты
   - `docs: ...` — документация
   - `chore: ...` — настройка, CI
6. **CI должен быть зелёным** перед merge.

### Типовой цикл работы

```
1. Взять задачу из GitHub Projects (статус To Do → In Progress)
2. git checkout -b feat/points-system
3. Писать код, коммитить маленькими шагами
4. git push origin feat/points-system
5. Открыть PR, описать что сделал, попросить ревью
6. Напарник ревьюит, оставляет комментарии (и/или бот ревью — см. §10.2)
7. Исправить замечания, дождаться зелёного CI
8. Merge в main (squash), удалить ветку
9. Задача → Done
```

### Советы для новичков

- **Ревью — это нормально.** Комментарии напарника — не критика, а способ
  сделать код лучше. Ревьюйте и вы — это лучший способ учиться.
- **Коммитьте часто и маленькими кусками.** Один коммит = одна логическая правка.
- **Пишите осмысленные сообщения коммитов**, а не "fix", "upd", "asdf".
- **Не сидите в задаче дольше 2–3 дней.** Если застряли — делитесь проблемой
  с напарником, делайте PR "в черновике" (draft) и просите помощи.
- **Синхронизируйте `main` перед началом новой задачи:** `git pull origin main`.

## 7. Словарь терминов (для новичка)

| Термин | Что значит |
|---|---|
| **REST API** | стиль API: ресурсы = URL, действия = HTTP-методы (GET/POST/PUT/DELETE) |
| **Endpoint** | конкретный URL + метод, например `POST /api/v1/auth/login` |
| **JWT** | JSON Web Token: подписанный токен, внутри которого user_id и срок жизни |
| **Access token** | короткоживущий токен (15–30 мин) для каждого запроса |
| **Refresh token** | долгоживущий токен для получения нового access без ввода пароля |
| **Ротация токенов** | при обновлении access старый refresh отзывается, выдаётся новый |
| **bcrypt** | алгоритм хеширования паролей (односторонний, с "солью") |
| **Middleware** | прослойка, обрабатывающая запрос до/после хендлера (auth, роли, лимиты) |
| **Статус-коды** | 200 OK, 201 Created, 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable, 429 Too Many Requests, 500 Internal Error |
| **CRUD** | Create / Read / Update / Delete — базовые операции над ресурсом |
| **Repository** | паттерн: слой доступа к данным, скрывает SQL от бизнес-логики |
| **Migration** | версионирование схемы БД: файл с SQL-изменениями, применяемый по порядку |
| **Пагинация** | разбиение списка на страницы (`?page=2&limit=20` или курсором) |
| **Курсорная пагинация** | "дай следующие 20 после записи X" — не ломается при вставках |
| **Rate limiting** | ограничение частоты запросов (защита от спама) |
| **Fail-open** | если Redis недоступен — пропускаем запросы, а не блокируем всех |
| **Jitter** | случайная задержка, чтобы запросы не шли "пачкой" |
| **Idempotency-Key** | заголовок с уникальным id операции: повтор запроса не создаёт дубль |
| **Идемпотентность** | операцию можно повторить без побочных эффектов |
| **Lost update** | потерянное обновление: два запроса читают одно значение и перетирают друг друга |
| **Set-based** | обработка данных одним SQL-запросом вместо цикла построчно |
| **Composition root** | единственная точка, где собирается весь граф зависимостей |
| **Liveness / Readiness** | "процесс жив" / "готов принимать трафик" — разные вещи |
| **Reverse proxy** | сервер перед приложением: TLS, сжатие, отдача статики (Nginx) |
| **Pull-модель метрик** | приложение отдаёт `/metrics`, Prometheus сам забирает данные |
| **fasthttp** | альтернативная реализация HTTP в Go; Fiber построен на ней, а не на net/http |
| **ADR** | документ, фиксирующий важное архитектурное решение и его причины |
| **SemVer** | версионирование Major.Minor.Patch (0.33.1 = major 0, minor 33, patch 1) |
| **Squash merge** | слияние PR одним коммитом (история остаётся чистой) |
| **OpenAPI/Swagger** | формат описания API, по которому можно генерировать документацию |

## 8. Правила, которые легко забыть (и потом больно чинить)

Раздел добавлен в версии 2.0. Это вещи, которых **не было** в первой версии
документа, и каждая из них — известные грабли.

### 8.1. Баллы: конкурентность и идемпотентность

`POST /users/{id}/points` — единственный эндпоинт, где ошибка портит данные
безвозвратно. Два обязательных требования:

**1. Никакого read-modify-write в Go.**

❌ Так нельзя:
```go
user, _ := repo.GetByID(ctx, id)        // прочитали 100
user.AcademicPoints += 50               // посчитали в Go: 150
repo.Update(ctx, user)                  // записали 150 — второй параллельный
                                        // запрос тоже записал свои 150, +50 потеряно
```

✅ Так надо — арифметика и проверка инварианта в одном запросе:
```sql
UPDATE users
   SET academic_points = academic_points + $1
 WHERE id = $2
   AND academic_points + $1 >= 0        -- не даём уйти в минус
RETURNING academic_points;
```
Ноль строк в ответе → бизнес-правило нарушено → **422**, а не 500.
Это одновременно убирает lost update и запрещает отрицательный баланс.

**2. `Idempotency-Key` обязателен.**

Админ нажал кнопку, ответ не дошёл, админ нажал ещё раз — при наивной
реализации баллы начислятся дважды. Поэтому:
- клиент шлёт заголовок `Idempotency-Key: <uuid>`;
- в `points_transactions` есть `idempotency_key TEXT UNIQUE`;
- вставка идёт `ON CONFLICT (idempotency_key) DO NOTHING`;
- если конфликт — возвращаем **201 с той же транзакцией**, а не создаём новую.

Повтор по сети — это норма, а не край. Планируйте это сразу.

### 8.2. Рассылка: не цикл, а один запрос

В Python-версии рассылка в Telegram требовала bulk-размеров, concurrency,
jitter и retry — потому что каждое сообщение это сетевой вызов к Telegram API.

**В нашей версии доставка — это запись строки в БД.** Значит, весь этот
аппарат не нужен, и "защита от перегрузки БД" достигается тем, что мы
**не делаем цикл**:

✅ Один запрос вместо 10 000:
```sql
INSERT INTO notifications (user_id, text, broadcast_id, created_at)
SELECT u.id, $1, $2, now()
  FROM users u
  JOIN user_roles ur ON ur.user_id = u.id AND ur.role_id = $3   -- для target=role
 WHERE u.activity_status_id = 1;                                -- только активные
```

❌ 10 000 запросов в цикле с jitter — то, что делали в Python, и то, что на Go
не нужно.

Jitter/retry вернуть **только** если появится реальный внешний канал доставки
(email, push, Telegram-шлюз). Тогда это отдельная задача с отдельным воркером.

### 8.3. Миграции запускаются отдельно, а не из API

В первой версии документа не было сказано, как применяются миграции вообще.
Если запускать `migrate.Up()` при старте API, то при нескольких репликах
они начнут гонку за схему БД — это классическая причина битых деплоев.

**Правило:**
- миграции применяет **отдельный бинарник `cmd/migrate`**;
- в Compose это **one-shot сервис** `migrate`;
- в CD — **отдельный шаг до** раскатки новой версии API;
- `cmd/api/main.go` **никогда** не вызывает миграции.

### 8.4. Rate limiting: где, когда и что при отказе Redis

- **Где:** `/auth/login` и `/auth/register` — **Фаза 3** (не Фаза 11).
  Перебор пароля — не "улучшение", а часть аутентификации. Остальные
  эндпоинты — позже.
- **Ключ:** per-IP **и** per-account. Только per-IP не спасает от
  распределённого перебора; только per-account — позволяет заблокировать
  чужой аккаунт.
- **IP клиента:** обязательно через `X-Forwarded-For` (§9.2), иначе за
  Nginx все запросы будут выглядеть как один IP и лимит сработает
  для всех сразу.
- **Fail-open:** если Redis недоступен — **пропускаем** запросы, а не
  отвечаем 429 всем. Падение Redis не должно ронять API. Это осознанный
  компромисс: под атакой с мёртвым Redis мы без защиты, но без ложной
  блокировки живых пользователей. Альтернатива (fail-closed) хуже:
  недоступность Redis превращается в полный отказ сервиса.

### 8.5. Права: откуда берутся роли и кто такой админ

**Откуда middleware берёт роли.** Два варианта, нужно выбрать (ADR в Фазе 3):
- **читать роли из БД на каждом запросе** — всегда актуально, +1 запрос;
- **класть роли в JWT** — быстрее, но роль в токене устаревает на время его жизни.

**РЕШЕНИЕ:** роли в JWT + короткий TTL access-токена + `access_token_version`
(§4.2), который инкрементится при **любом изменении ролей**. Так роль
применяется мгновенно, а лишних запросов в БД нет.

**Правила, которые надо решить и записать (иначе получите дыру):**
- Может ли Admin выдать другую роль Admin? (по умолчанию — да, но осознанно)
- Можно ли снять роль Admin у последнего админа? (по умолчанию — **нет**, 422:
  иначе останетесь без админов и без способа их вернуть через API)
- Может ли пользователь запросить роль Admin через `role-requests`?
  (по умолчанию — **нет**: эскалация привилегий)
- `POST /users/{id}/roles` — самый опасный эндпоинт в API. Он обязан быть
  в `role_events` целиком: кто, кому, что, когда.

## 9. Инфраструктура (✅ новый раздел)

Замечание из `Redaction.md`: *"Docker compose — стоит уделить больше времени"*,
*"Балансировщик возможно стоит добавить: Nginx"*, *"Прикрутить систему
с метриками (Grafana & Prometheus)"*. Принимается, с уточнениями по фазам.

> ⚠️ **Не копируйте инфраструктуру Python-версии 1-в-1** (§2.1). В ней были
> Grafana+Loki+Alloy+Nginx+Ansible — для двух человек и учебного API это
> лишняя нагрузка. Ниже — та же функциональность, но добавляемая **по шагам**.

### 9.1. Docker Compose — на что реально потратить время

**Сервисы и порядок запуска:**

```yaml
services:
  postgres:   # с healthcheck: pg_isready
  redis:      # с healthcheck: redis-cli ping
  migrate:    # one-shot: применяет миграции и выходит с кодом 0
    depends_on:
      postgres: { condition: service_healthy }
  api:
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_healthy }
      migrate:  { condition: service_completed_successfully }   # ключевая строка
  worker:
    depends_on:
      migrate:  { condition: service_completed_successfully }
```

**Главная ошибка новичка:** написать `depends_on: [postgres]` без `condition`.
Тогда контейнеры стартуют одновременно, API пытается подключиться к ещё
не поднявшейся БД и падает в crash-loop. `service_healthy` +
`service_completed_successfully` решают это.

**Что ещё решить (и записать в ADR):**
- **Тома:** данные `postgres` — в именованном volume, иначе `docker compose down`
  стирает базу. Redis — нужна ли персистентность (AOF), или он у нас кэш.
- **Порты:** наружу публикуем **только** Nginx (80/443) и, для отладки,
  Postgres. API и `/metrics` — во внутреннюю сеть.
- **Env:** один `.env.example` в репозитории с полным списком переменных.
  (В Python-версии были десятки переменных без образца — так делать не надо.)
- **Два файла:** `docker-compose.yml` для разработки (с монтированием кода),
  `docker-compose.prod.yml` для продакшна (только собранные образы).

### 9.2. Nginx — зачем он на самом деле нужен

**Плохая причина:** "добавить балансировщик". У нас одна реплика API и нет
трафика — балансировать нечего.

**Настоящие причины поставить Nginx рано:**
1. **TLS-терминация** — Go-сервер не должен заниматься сертификатами.
2. **`X-Forwarded-For` / `X-Real-IP`** — и это ключевое. Если подключить
   rate limiting (§8.4) до появления прокси, он будет считать `RemoteAddr`,
   работать локально и **сломаться на проде**: за прокси все запросы придут
   с одного IP. Один общий лимит на всех пользователей.
   → **Порядок работ:** сначала middleware умеет читать `X-Forwarded-For`
   (Фаза 3), потом появляется Nginx (Фаза 10). Не наоборот.
3. **Закрыть `/metrics` и `/health` снаружи** — служебные эндпоинты не должны
   быть доступны из интернета.
4. Отдача статики (если появится веб-клиент), gzip, ограничение размера тела.

**Что НЕ надо делать:** ставить Nginx в Фазу 1. Сначала API, который работает
напрямую, потом прокси перед ним. Иначе будете отлаживать два слоя сразу.

### 9.3. Метрики: Prometheus + Grafana

**Модель — pull, не push.** Приложение ничего никуда не отправляет; оно отдаёт
`GET /metrics` в формате Prometheus, а Prometheus сам периодически его забирает.

**Что делать в Фазе 1 (дёшево сейчас, дорого потом):**
- подключить `prometheus/client_golang`;
- метрики по умолчанию: счётчик запросов по маршруту и коду ответа,
  гистограмма длительности, счётчик ошибок;
- gauge готовности: результат проверок БД и Redis из `/ready` — удобно
  видеть на графике, когда именно сервис "не готов".

**Что делать в Фазе 10 (когда есть на что смотреть):**
- сервис `prometheus` со scrape-конфигом на `api:8080/metrics`;
- сервис `grafana` с дашбордом: RPS, p95/p99 задержки, доля 5xx,
  пул соединений к БД;
- `node-exporter` / `cadvisor` — **только если реально понадобятся**.

**Почему не в Фазе 1:** Prometheus + Grafana + exporters превращают
3 сервиса в 7–9 контейнеров. Инструментировать надо сразу (это дёшево),
а вот разворачивать и настраивать дашборды — когда появились данные.

### 9.4. Liveness ≠ Readiness (уточнение контракта)

В первой версии документа это не было разделено, а разница принципиальная:

| | `/health` (liveness) | `/ready` (readiness) |
|---|---|---|
| Смысл | "процесс не завис" | "готов принимать трафик" |
| Что проверяет | ничего, просто 200 | БД, Redis |
| Реакция | перезапустить контейнер | **убрать из балансировки** |
| При падении БД | 200 (перезапуск не поможет) | 503 (трафик уходит на другую реплику) |

**Правильный порядок деплоя:** поднять новый инстанс → он отдаёт 503 на
`/ready`, пока не прогрелся → дождаться 200 на `/ready` → переключить трафик →
погасить старый. Если `/ready` вернуть неправильно, трафик пойдёт на
непрогретый инстанс и пользователи получат 500.

## 10. ИИ-ментор (DeepSeek) и GitHub (✅ новый раздел)

Замечание из `Redaction.md`: *"GitHub канбан доска & ментор ИИ (DeepSeek) как-то
подключить к GitHub проекту чтоб имел контекст и выставлял нам таски в канбан доске"*.

### 10.1. Как это устроено на самом деле

**Важно понимать: готовой интеграции "DeepSeek ↔ GitHub Projects" не существует.**
DeepSeek предоставляет API для генерации текста; клиента GitHub Projects у него нет.
Найденные в поиске "интеграции" DeepSeek+GitHub — это сторонние low-code платформы
автоматизации (Workato и подобные), платные и не предназначенные для учебного проекта.
Строить на них workflow не стоит.

Значит, если хочется — это **свой скрипт**, и вот его устройство:

**Ключевой факт: GitHub Projects v2 управляется только через GraphQL.**
REST API доски Projects v2 не умеет (там остался только legacy Projects classic).
Нужные операции:
- добавить элемент на доску — мутация `addProjectV2ItemById`;
- перевести в колонку — мутация `updateProjectV2ItemFieldValue` по полю Status;
- нужен **node ID проекта**, а не номер из URL;
- `GITHUB_TOKEN` в Actions обычно **не имеет** прав на Projects → нужен
  отдельный PAT со scope `project`, положенный в секреты репозитория.

**Механика:** GitHub Action с триггером `schedule:` (+ `workflow_dispatch:`
для ручного запуска), который дёргает DeepSeek API, получает список задач
и создаёт их через GraphQL-мутации.

### 10.2. Что я рекомендую сделать вместо этого

**Проблема с исходной идеей:** ИИ, который сам придумывает и заводит задачи,
за редким исключением генерирует мусор в канбане. Доска из 60 задач
"написал функцию", "добавил обработку ошибок" хуже пустой доски — её перестают
читать. **Ваш бэклог не является узким местом:** `GO_ROADMAP.md` уже есть
готовый пофазный чеклист с галочками. Узкое место — прогресс и обратная связь.

**Поэтому предлагаю другой первый шаг — бот ревью PR:**

| | ИИ заводит задачи | **ИИ ревьюит PR** ← рекомендуем |
|---|---|---|
| Что делает | придумывает задачи в канбан | комментирует код в PR |
| Ценность | низкая (задачи уже есть) | высокая |
| Совпадает с целью | нет | **да** — §6: "ревью — лучший способ учиться" |
| Сложность | GraphQL + PAT + провижининг доски | один workflow + один секрет |
| Риск мусора | высокий | низкий (комментарии, не задачи) |

**Устройство бота ревью:**
1. файл `.github/workflows/ai-review.yml`, триггер `on: pull_request`;
2. шаг: забрать диф (`gh pr diff` или REST API);
3. шаг: отправить диф в DeepSeek API с системным промптом
   ("ты ревьюер Go-кода; укажи идиоматичность, обработку ошибок,
   конкурентность, тесты; будь конкретен, ссылайся на строки");
4. шаг: опубликовать ответ комментарием к PR (`gh pr comment`);
5. секрет `DEEPSEEK_API_KEY` в настройках репозитория.

**Важные ограничения, чтобы не разочароваться:**
- это **вспомогательное** ревью, оно **не заменяет** ревью напарника (§6.1);
- диффы бывают большими — нужен лимит на размер и обрезка;
- боту нельзя давать права на merge и на запись в код;
- первое время запускайте его в режиме комментария, без блокировки PR.

### 10.3. Если всё-таки нужна автоматизация канбана

Тогда делайте её **второй**, после бота ревью, и с ограничениями:
- ИИ создаёт задачи **в статусе To Do** и **только из явного источника** —
  например, из отмеченных чекбоксов в `GO_ROADMAP.md`, а не "из головы";
- **обязательна дедупликация:** перед созданием задачи искать существующую
  по названию, иначе каждый запуск плодит дубли;
- запуск **вручную** (`workflow_dispatch`), а не по расписанию: по расписанию
  мусор накапливается незаметно;
- ИИ **не двигает** задачи в In Progress/Done — статус отражает реальную работу,
  и его меняет человек.

**Порядок внедрения:** сначала §10.2 (бот ревью), потом §10.3 (канбан),
и только если доска действительно стала узким местом.
